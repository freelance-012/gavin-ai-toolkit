# Phase 3: 验证

## 目标

用生成的 spec 中的信息尝试实际操作（读取数据、运行评估脚本），验证 spec 的正确性和可解析性。发现错误则回到 Phase 1 修正。

## 触发词

- "验证 spec"
- "检查规格"

## 依赖

Phase 2 生成的 `project-spec.md`

## 输入参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| project_path | string | ✅ | 项目根目录绝对路径 |
| spec_path | string | ✅ | `{project}/.specs/project-spec.md` |

## 输出产物

更新 `{project}/.specs/project-spec.md`（修正验证中发现的错误）

## 执行步骤

### Step 1: 验证数据路径

**1.1 检查数据目录是否存在**

读取 spec 中 `## 数据集` 章节，验证：
- 数据目录是否存在
- 目录结构是否与 spec 描述一致
- 是否能找到图像文件

```bash
# 示例验证
ls {数据目录} | head -5
# 检查是否符合预期的子目录结构
```

**1.2 验证真值文件**

读取 spec 中 `## 真值` 章节，验证：
- 真值文件是否存在
- 文件是否可以读取
- 格式是否与 spec 描述一致

```bash
# 读取前几行验证格式
head -3 {真值文件路径}
```

对比实际内容与 spec 中描述的格式：
- 列数是否匹配
- 时间戳量级是否合理（秒 vs 纳秒）
- 坐标值量级是否合理

**1.3 验证轨迹输出**

如果存在之前的运行结果，检查：
- 轨迹文件是否存在
- 格式是否与 spec 描述一致

### Step 2: 验证评估脚本

读取 spec 中 `## 评估` 章节，验证：
- 评估脚本是否存在
- 脚本是否可执行
- 尝试以 `--help` 或无参数运行，查看输出
- 检查输出格式是否与 spec 描述一致

```bash
# 检查脚本是否存在
ls -la {评估脚本路径}

# 尝试获取帮助信息
python {评估脚本路径} --help 2>&1 | head -20
# 或
{评估脚本路径} --help 2>&1 | head -20
```

> ⚠️ 不实际运行完整评估（可能需要较长时间），只验证脚本存在性和基本可执行性。

### Step 3: 验证日志

读取 spec 中 `## 日志` 章节，验证：
- 如果存在之前的日志文件，检查格式是否匹配
- 检查日志中的模块名是否与 spec 中列出的一致

```bash
# 如果有日志文件
head -5 {日志文件路径}
# 搜索 spec 中提到的模块名
grep "{模块名}" {日志文件路径} | head -3
```

如果没有已有日志，跳过此步，标注"待运行后验证"。

### Step 4: 汇总验证结果

```markdown
🔍 **验证结果**

### 通过 ✅
| # | 验证项 | 状态 |
|---|--------|------|
| 1 | 数据目录存在且结构正确 | ✅ |
| 2 | 真值文件可读，格式匹配 | ✅ |
| ... | ... | ... |

### 失败 ❌
| # | 验证项 | 问题 | 建议修正 |
|---|--------|------|---------|
| 1 | 真值文件格式 | 实际为 8 列，spec 描述为 9 列 | 修正 spec 中的格式描述 |
| ... | ... | ... | ... |

### 无法验证 ⚠️
| # | 验证项 | 原因 |
|---|--------|------|
| 1 | 轨迹输出格式 | 无已有运行结果 |
| ... | ... | ... |
```

### Step 5: 修正 spec（如有错误）

如果验证发现错误：
1. 自动修正 spec 中的错误项
2. 更新 spec 文件的"最后更新"日期
3. 标注修正来源为"Phase 3 验证修正"

如果错误较多或涉及用户指定的关键信息（如真值格式），需要回到 Phase 1 让用户确认。

### Step 6: 最终报告

```markdown

  - 总条目: {N} 项
  - 已验证: {N} 项
  - 待验证: {N} 项（需要实际运行后验证）

该 spec 文件可供以下 skill 使用:
  - slam-debug-helper（调试排查）
  - slam-eval-runner（轨迹评估）
  - slam-log-analyzer（日志分析）
  - slam-perf-optimizer（性能优化迭代）

如需更新，运行: "更新项目规格"
```

## 注意事项

1. **非破坏性验证**：Phase 3 只做读取和检查，不实际运行 SLAM 系统或修改项目代码
2. **自动修正**：格式层面的错误（如列数、路径）自动修正，语义层面的错误（如指标含义）需要用户确认
3. **不阻塞**：部分项无法验证时（如无已有运行结果），标注"待验证"但不阻塞流程
4. **记录验证状态**：在 spec 文件末尾添加"验证状态"章节，记录各项的验证结果
