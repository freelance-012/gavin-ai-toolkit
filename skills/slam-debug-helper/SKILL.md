# slam-debug-helper

SLAM 系统故障诊断与修复助手。从症状出发，通过决策树定位根因，给出可操作的修复方案。

## 定位

**诊断 skill**——当 SLAM 系统出现问题时，帮助用户从现象到根因到修复。

**核心原则**：
- 基于症状分类，使用决策树系统排查
- 结合 eval-runner 的评估结果和 log-analyzer 的日志分析
- 给出可验证的修复方案，而非泛泛建议

## 触发词

- "系统发散了"
- "轨迹漂移"
- "跟踪丢失"
- "初始化失败"
- "回环检测失败"
- "SLAM 出问题了"
- "debug"

## 依赖

- `project-spec.md`（由 slam-project-profiler 生成）
- 可选：eval-runner 的评估结果
- 可选：log-analyzer 的日志分析结果

## 输入参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| project_path | string | ✅ | 项目根目录绝对路径 |
| symptom | string | ⬜ | 症状描述（如"轨迹发散"、"跟踪丢失"） |

## 输出产物

```
{project}/.specs/debug/
└── {timestamp}_{session_id}/
    ├── debug-report.md              # 诊断报告
    └── fix-suggestions.md           # 修复方案（可操作的步骤）
```

## 四步法工作流

```
Phase 0: 症状分类      → 确定故障类型（漂移/发散/丢失/初始化失败/回环失败）
Phase 1: 信息收集      → 读取 spec + eval 结果 + 日志 + 参数配置
Phase 2: 根因诊断      → 按故障类型的决策树逐层排查
Phase 3: 修复方案      → 给出可操作的修复步骤 + 验证方法
```

### 依赖关系

```
Phase 0 ──────→ Phase 1 ──────→ Phase 2 ──────→ Phase 3
（症状分类）     （信息收集）      （根因诊断）      （修复方案）
```

## 执行模式

### 模式 A：完整诊断（默认）

用户说："系统发散了，帮我诊断" 或 "debug"

执行流程：
1. 检查 spec 文件是否存在
2. 按 Phase 0 → 1 → 2 → 3 顺序执行
3. 生成诊断报告和修复方案

### 模式 B：指定症状诊断

用户说："轨迹漂移，帮我看看原因"

执行流程：
1. 跳过 Phase 0（症状已明确）
2. 直接进入 Phase 1 → 2 → 3

### 模式 C：仅根因诊断

用户说："我已经收集了日志，帮我分析根因"

执行流程：
1. 跳过 Phase 0 和 Phase 1
2. 直接进入 Phase 2 → 3

## Phase 编排详情

| Phase | 文件 | 名称 | 可独立执行 |
|-------|------|------|-----------|
| 0 | `phases/phase0-symptom.md` | 症状分类 | ✅ |

## 故障类型与决策树

### 轨迹漂移（Drift）

**症状**：轨迹随时间逐渐偏离真值，误差单调增长

**常见根因**：
1. 尺度模糊（单目系统）
2. IMU 零偏未标定或估计不准
3. 外参旋转矩阵错误
4. 特征跟踪不稳定
5. 优化收敛到局部最优

### 轨迹发散（Divergence）

**症状**：轨迹快速偏离，误差急剧增大，系统完全失效

**常见根因**：
1. 外参平移量级错误（mm vs m）
2. 时间戳偏移过大
3. 噪声参数不合理（过大或过小）
4. 坐标系定义不一致（FLU vs ENU vs NED）
5. 初始化失败但系统继续运行

### 跟踪丢失（Tracking Loss）

**症状**：特征点跟踪突然中断，系统无法继续估计位姿

**常见根因**：
1. 运动过快（超过特征跟踪能力）
2. 特征数量太少（纹理不足）
3. 基线太短（双目/双目+IMU）
4. 遮挡或动态物体干扰
5. 相机曝光问题（过曝/欠曝）

### 初始化失败（Initialization Failure）

**症状**：系统无法完成初始化，无法开始正常估计

**常见根因**：
1. 运动激励不足（需要特定运动模式）
2. 特征分布不均（集中在平面或边缘）
3. IMU 和相机时间未同步
4. 外参初始值太差
5. 场景纹理不足

### 回环检测失败（Loop Closure Failure）

**症状**：无法检测到已经访问过的地方，或检测到错误的回环

**常见根因**：
1. 描述子阈值设置不当
2. 几何验证容差过严或过松
3. 关键帧选取策略不合理
4. 感知混叠（不同地方看起来相似）
5. 回环候选筛选逻辑错误

## 全局约定

### 诊断报告格式

诊断报告必须包含：
1. 症状描述
2. 收集的信息（评估结果、日志片段、参数配置）
3. 根因分析（决策树路径）
4. 置信度评估（高/中/低）
5. 修复方案（具体步骤）
6. 验证方法（如何确认修复有效）

### 修复方案要求

修复方案必须是**可操作的**：
- ❌ "调整参数" → ✅ "将 IMU 陀螺仪噪声从 0.01 改为 0.001"
- ❌ "检查外参" → ✅ "检查 config/extrinsic.yaml 中的 T_cam_imu，确认平移单位是米"
- ❌ "优化特征提取" → ✅ "增加特征点数量：将 MAX_FEATURES 从 150 改为 300"

### 与其他 skill 的衔接

本 skill 可以读取以下 skill 的产出：

| 提供方 skill | 读取的内容 |
|-------------|-----------|
| slam-eval-runner | 误差时序、异常区间、评估指标 |
| slam-log-analyzer | 日志分析结果、关键日志片段 |
| slam-project-profiler | 项目规格（数据集、参数、日志格式） |

### 错误处理

当 spec 文件缺失时：

```
⚠️ 无法执行 slam-debug-helper

原因: 缺少项目规格文件:
  - {project}/.specs/project-spec.md

解决方案:
  先执行 slam-project-profiler 生成项目规格

是否需要我帮你执行 profiler？(Y/n)
```

当无法确定根因时：

```
⚠️ 无法确定根因

已排查的可能原因:
1. {原因1} - 已排除（{理由}）
2. {原因2} - 无法验证（{缺少什么信息}）
3. {原因3} - 可能是根因（置信度: 中）

建议:
1. 添加调试日志: {具体位置和内容}
2. 重新运行系统，收集更多日志
3. 再次运行 debug-helper 分析新日志
```
